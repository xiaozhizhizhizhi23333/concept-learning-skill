2核心问题（带着问题读）

同样一句话，为什么"写进提示词"和"做成一个 Skill"，价值不一样？
Skill 的 description 到底有什么用？为什么它对"能不能被自动触发"至关重要？
项目级和用户级 Skill 各放在哪里？什么时候该用哪一种？

3个人解释

Skill 就是"打包成文件、可随时被加载复用的任务操作手册"。它把"某类任务该怎么做"写清楚——包括流程、要点、注意事项——并存成一个 SKILL.md 文件。当 AI 需要做这类任务时，就"翻开"这本手册照着做，而不是每次都靠临时临场发挥。

打个比方（个人理解）：提示词像是"口头上交代一次"；Skill 像是"写成一本随时可查、可更新、可传给别人的操作手册"。因为它是文件，所以可以放进 Git 版本管理、可以沉淀、可以团队共享。

4核心机制 / 组成

组成说明
YAML 元数据（name + description）放在 SKILL.md 顶部。其中 description 说明"做什么、何时用"，是 AI 判断是否触发该 Skill 的匹配依据。
指令正文写清适用场景、输入、步骤、输出结构、来源与自检要求等程序性知识。
可选资源可附带脚本、模板、参考资料等，在需要时才被加载（"渐进式披露"，省上下文）。
存放位置（作用域）用户级：~/.workbuddy/skills/，跨项目通用；项目级：<项目>/.workbuddy/skills/，只在本项目内生效、可随仓库共享。

5一个具体应用场景

本作业就是活例子：把"概念学习资料怎么生成"这一套固定流程，沉淀成一个项目级 Skill（.workbuddy/skills/concept-learning-generator/SKILL.md）。以后只要说"学习概念：XXX"，它就能按同一套栏目（学习目标 → 核心问题 → 解释 → 机制 → 场景 → 辨析 → 自测 → 来源）自动生成新概念的资料，不用每次重新写提示词。

6易混淆点 / 使用边界

① Skill ≠ 一次性提示词：提示词只作用于一次对话；Skill 是可复用、可沉淀、可版本管理、可随仓库/团队共享的"工作流程资产"。
② 项目级 vs 用户级：项目级（.workbuddy/skills/）随项目仓库走、便于共享和作业提交；用户级（~/.workbuddy/skills/）只在你本机、跨项目通用。别把两者混放。
③ 边界：Skill 不是"让模型变聪明"，而是"把怎么做写清楚"。如果手册本身写得含糊、过时，执行效果也不会好——Skill 需要像代码一样持续维护。
